## 引言

引入一个基础场景用于后续的说明

场景：假设我们正在开发一个企业级文档管理系统。在这个系统中有基本的需求如下：

- 企业内部分为多个不同部门
- **部门内的员工可访问部门内的公开文档，非部门成员则不可访问部门内的文档**
- 文档本身包含密级（秘密、机密、绝密），不同密级的文档需要不同权限的员工才能访问
- 文档创建者本身拥有文档的完整权限

部门： 研发部门、产品部门、经理办公室

员工：

- 研发部门： 研发 A, 研发 B, 研发 C
- 产品部门： 产品 A, 产品 B, 产品 C
- 经理办公室： 经理 A, 经理 B, 经理 C

## 常见的权限模型概述

### PBAC（Policy-Based Access Control） 基于策略的访问控制：

针对每个权限配置策略，对不同的用户逐个分配拥有的权限，这个模型的特点是实现简单、灵活性较好但是配置复用困难，例如：

当产品内部讨论需求时共同维护一份**产品文档 A**，此时需要为每个产品同学添加**产品文档 A**的权限，

当产品同开发同学对接需求时，则需要将**产品文档 A**的权限再配置给开发同学

在文档数量和员工数量少的情况下，这种权限模型是比较简单的，但是当文档数量和员工数量增多时，这种权限模型的修改就会变得十分复杂以至于不可维护，例如：

当有一个产品涉及到 10 个产品和 10 个研发参与时，将会产生非常麻烦的重复编辑权限的情况

又如，当研发团队新招聘到一位同学时，需要给这位同学逐个添加非常多开发部门基本说明的相关文档。

当规模达到一定程度时使用这种权限模型显然是不合理的。

### RBAC（Role-Based Access Control） 基于角色的访问控制：

基于角色的访问控制，易于批量管理，实现相对简单，

实现思路是用户和权限的分离，通过新加角色中间层实现权限的批量编辑，例如：

系统中可以包含一个角色**研发部员工**，同时将所有研发部门的基本说明文档的访问权限配置给这个角色，

这样当我们新招聘到一个研发同学时，可以将**研发部员工**的角色添加给他，这样他就会自动获取到所有研发部门的基本说明文档的访问权限，而不再需要一个文档一个文档的添加权限。

同时当某个文档的内容过时需要删除时，也可以通过编辑**研发部员工**角色的权限来实现，而不需要逐个删除每个研发同学的权限。

但是 RBAC 仍有一些局限性，例如：

#### 角色数量爆炸

随着系统复杂度增加，角色数量会极速膨胀，导致管理困难

在一个大型系统中，不同部门、职位和权限组合可能导致成千上万的角色，增加了管理负担，例如：

研发部门分为三个项目组，每个项目组中的文档又分为三个密级，此时研发部门将拥有 3 \* 3 = 9 个角色

可以看到角色的数量随着判别条件的增加是指数级增长的，这很容易导致角色数量爆炸

#### 缺乏细粒度控制

例如，当项目组长 A 想要将某个密级为绝密的文档临时开放给某个指定的项目成员 B，此时角色模型就不能很好的完成这个需求

可能需要通过单独的创建一个角色来应对这个需求，当这种灵活的需求变多后仍然会面对管理混乱的场景

又比如，为了保证信息安全，绝密文档只能在公司内网的 ip 时才能访问，在这种场景下 RBAC 就会失效，无法表达这个权限

...

RBAC 还有许多变体，弥补了 RBAC 本身的一些缺陷，但是基于角色的表达方式本身的缺陷始终制约着 RBAC 的灵活性

### ABAC（Attribute-Based Access Control） 基于属性的访问控制：

ABAC 是一种动态的访问控制模型，通过评估主体（用户）、资源（对象）、环境（上下文）和操作的属性来决定是否允许访问。

#### ABAC 的核心要素

**主体属性（Subject Attributes）：**

描述用户的身份、职位、部门、角色等

**资源属性（Object Attributes）：**

描述被访问资源的特性，如类型、所属部门、保密级别等

**环境属性（Environment Attributes）：**

描述访问发生的上下文条件，如时间、地理位置、设备类型等

**操作（Action）：**

用户对资源的具体操作，如 读取、写入、删除

#### TypeScript 中的 ABAC 实践

代码实现：

定义用户、资源和环境属性。

实现策略评估逻辑。

代码示例：

```typescript
interface User {
  role: string;
  department: string;
}

interface Resource {
  type: string;
  owner: string;
}

interface Environment {
  time: Date;
  ipAddress: string;
}

function evaluatePolicy(
  user: User,
  resource: Resource,
  environment: Environment,
): boolean {
  // 示例策略：只有管理员在工作时间可以访问机密文件
  const isAdmin = user.role === 'admin';
  const isConfidential = resource.type === 'confidential';
  const isWorkingHours =
    environment.time.getHours() >= 9 && environment.time.getHours() <= 17;

  return isAdmin && isConfidential && isWorkingHours;
}

function enforceAccess(
  user: User,
  resource: Resource,
  environment: Environment,
): string {
  const isAllowed = evaluatePolicy(user, resource, environment);
  return isAllowed ? 'Access granted' : 'Access denied';
}

// 示例调用
const user: User = { role: 'admin', department: 'IT' };
const resource: Resource = { type: 'confidential', owner: 'company' };
const environment: Environment = { time: new Date(), ipAddress: '192.168.1.1' };

console.log(enforceAccess(user, resource, environment)); // 输出 "Access granted" 或 "Access denied" 6. ABAC 的挑战与注意事项
```

复杂性：ABAC 的实现和维护比 RBAC 更复杂。

性能开销：动态评估策略可能带来性能开销，尤其是在大规模系统中。

策略管理：需要良好的策略管理工具，避免策略冲突和混乱。
