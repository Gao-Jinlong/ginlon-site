# LangGraph Checkpointer 检查点机制学习笔记
## 一、核心基础概念
### 1. Checkpoint（检查点/StateSnapshot 状态快照）
1. 生成时机：Graph 每完成一次 Super-step（一轮节点执行），自动生成一份完整检查点；
2. 存储内容：**当前时间点完整全局 State**，不只是对话消息：
   - 完整 messages 全量对话列表；
   - 自定义业务状态字段、工具返回结果、变量缓存；
   - 流程控制元数据：下一步待执行节点、唯一 checkpoint_id、父快照关联信息、会话配置等；
3. 存储形式：每份快照是独立、只读、完整副本，非增量差分存储。

### 2. Thread（会话线程）
- 隔离单位：一个独立对话/任务对应唯一 `thread_id`；
- 存储关系：单个 Thread 下有序存放该会话全部历史 Checkpoint；
- 作用：不同用户、不同对话状态天然隔离，互不干扰。

### 3. Super-step 超步
- 串行节点：每个节点执行完成单独占用一个超步；
- 并行节点：一批并行节点共用同一个超步；
- 绑定规则：每完成一次超步，强制持久化一份 Checkpoint。

### 4. Checkpointer
负责所有 Checkpoint 的持久化、读取、历史查询底层存储实现，是快照读写底层载体。

## 二、两大核心状态查询 API
1. `graph.get_state(config)`
   获取当前 Thread **最新一份状态快照**，用于查看当前对话进度、最新上下文。
2. `graph.get_state_history(config)`
   获取当前 Thread 下**全部历史 Checkpoint 数组**，按执行时间排序，是实现时间旅行、分支对话的核心能力入口。

## 三、分支对话（时间旅行）核心原理（本次重点讨论场景）
### 场景举例
原始对话链路：A → B → C
操作：从 B 节点的历史快照分叉出新对话 B → C1
### 关键结论
1. **新旧分支完全并存，原始链路不会被覆盖/删除**
   从历史 checkpoint 重启执行只会追加新快照到 Thread 历史列表，原有 A/B/C 快照永久保留，`get_state_history` 可同时查到 A、B、C、C1 四份完整快照。
2. **可以随时切回原始对话 C 继续推进**
   通过 `get_state_history` 找到 checkpoint_C 对应的快照配置，传入 `invoke` 执行，即可回到原始时间线继续对话，新分支 C1 仍完整保存在历史中不受影响。
3. 支持两种分叉模式
   - 同 Thread 分叉（推荐体验多路线试错）：共用一套历史快照，随时来回切换分支；
   - 新建 Thread 分叉（完全隔离）：复制 B 的 state 分配新 `thread_id`，两条对话彻底独立，互不干扰。

### 为什么能实现多分支？（解答核心疑问）
实现分支对话的必要前提：**每一份 Checkpoint 都存储该时刻完整的 State（包含完整 messages 列表）**
1. 若采用增量存储（仅存新增消息）：无法从中间节点分叉出两条独立对话链路；
2. 全量快照设计：B 的快照自带 A+B 完整消息，基于它生成 C1 时会生成独立的 [A,B,C1] 消息副本；原有 C 快照保留 [A,B,C] 完整消息，两条分支上下文完全独立。
3. 补充区分两层逻辑：
   - 运行内存：节点更新 state 时增量追加消息（`add_messages`）；
   - 持久化存储：落盘为完整快照，不做增量存储，是分支能力根基。

## 四、官方文档关键原文提炼
1. 从检查点恢复执行不会删除原始时间线，所有历史快照永久保留，不会丢失对话记录；
2. 回滚历史节点重新执行会创建对话时间线分支，仅线程“最新状态指针”切换至新快照，旧快照完整留存于历史列表；
3. 所有 Checkpoint 快照只读，分叉操作仅新增快照，不会修改、覆盖任何已存档历史数据。

## 五、常见误区澄清
1. 误区：分叉出新路线后，原来的对话记录 C 会消失
   纠正：仅当前最新快照变为 C1，C 完整保存在历史快照中，可随时回切；
2. 误区：Checkpoint 只存储对话 messages
   纠正：存储完整全局 State，包含所有业务变量、流程执行现场、控制元数据；
3. 误区：同一 Thread 只能保留一条对话链路
   纠正：单 Thread 支持无限多分支并存，依靠全量快照实现多时间线共存。

## 六、整体执行流程示例
1. 初始化 Thread，初始状态，依次执行 A、B、C，生成 3 份独立快照存入线程历史；
2. 查询历史拿到 B 节点快照的配置信息；
3. 使用 B 的快照配置重新调用 invoke，执行新逻辑生成 C1 快照（新分支）；
4. 调用 `get_state_history` 可读取全部 4 份快照 A/B/C/C1；
5. 如需回到原始对话，读取 C 的快照配置执行 invoke，继续沿原始 A→B→C 链路推进。

## 七、Checkpointer 机制整体价值
1. 断点续跑：任务中断后可从任意快照恢复执行；
2. 对话分支试错：同一会话多条思路并行尝试，不用重复构建上下文；
3. 流程复盘审计：读取全量历史快照，完整还原每一步对话与状态变化；
4. 状态持久化：会话不丢失，支持长时间多轮对话存储。
